# Frontend Specification
## Wayzyy AI Trip Concierge — PS2

---

## 1. Frontend Goal

The frontend exists primarily to make the hackathon demo understandable and to trigger a realistic booking-to-concierge flow.

The guest-facing conversational experience is Telegram in the MVP.

Therefore, do not spend hackathon time building a full travel application unless the core workflow is already stable.

---

## 2. Frontend Components

### MVP frontend
1. Booking Simulator page.
2. Booking success/trigger state.
3. Optional demo status panel.

### Guest interface
Telegram bot.

---

## 3. Booking Simulator

### Purpose
Simulate the moment a guest completes a Wayzyy booking.

### Page layout

```text
┌─────────────────────────────────────────┐
│              WAYZYY                     │
│        AI Trip Concierge Demo            │
├─────────────────────────────────────────┤
│ Guest Name        [________________]     │
│ Property          [________________]     │
│ Area              [Candolim ▼]           │
│ Check-in          [YYYY-MM-DD]           │
│ Check-out         [YYYY-MM-DD]           │
│ Guests            [2 ▼]                  │
│ Telegram Chat ID  [________________]     │
│                                         │
│        [ Confirm Booking ]              │
├─────────────────────────────────────────┤
│ Status: Waiting for booking             │
└─────────────────────────────────────────┘
```

For the final hackathon demo, the fields can be pre-filled with the worked Candolim scenario.

---

## 4. Form Validation

Required:
- Guest name.
- Property.
- Area.
- Check-in.
- Check-out.
- Guest count.
- Telegram chat identifier if required by the workflow.

Validation:
- Check-out must be after check-in.
- Guest count must be positive.
- Dates must be valid.
- Required fields cannot be empty.

Do not validate or expose API secrets in the browser.

---

## 5. Booking Submission

On submit:

```text
Frontend
  ↓ POST
n8n Booking Webhook
  ↓
Itinerary Workflow
```

The frontend should show:
- Submission started.
- Booking accepted.
- Concierge activated.
- Itinerary being generated.
- Success/failure state.

Do not wait indefinitely. Provide a clear timeout/error state.

---

## 6. Demo Status

A simple status panel can show:

```text
✓ Booking confirmed
✓ Concierge activated
✓ Booking context loaded
✓ Goa recommendations loaded
✓ Itinerary generated
✓ Sent to Telegram
```

This is optional but useful for judges because it makes the automation visible.

---

## 7. Visual Design Direction

The frontend should communicate:
- Travel.
- Local expertise.
- Trust.
- Modern AI assistance.

Keep it clean rather than over-designed.

Suggested visual hierarchy:
1. Wayzyy identity.
2. “AI Trip Concierge” product name.
3. Booking details.
4. Primary booking button.
5. Live workflow status.

Use responsive design so it works on a laptop during judging and remains usable on mobile.

---

## 8. Telegram Message Specification

### Itinerary

Structure:

```text
🌴 Your Wayzyy Trip Plan

📍 Candolim
🗓 4 nights

DAY 1 — [Theme]
09:00 — [Activity]
13:00 — [Food]
17:30 — [Activity]

DAY 2 — [Theme]
...

Tip: [short local/context tip]
```

Do not make messages excessively long.

---

## 9. Proactive Weather Message

Preferred structure:

```text
🌧 Weather update for tomorrow

Rain is expected around your area, so I’ve adjusted your outdoor plan.

Instead of:
• [Outdoor activity]

Try:
• [Trusted alternative]

Your updated plan is ready.
```

The exact wording is generated by the notification agent, but the UX should remain concise and actionable.

---

## 10. Conversational Response

Responses should:
- Directly answer the guest.
- Use current booking context.
- Mention relevant nearby options.
- Avoid unnecessary essays.
- Offer one useful next step where appropriate.

Example:

```text
You’re staying in Candolim, so for dinner I’d keep it nearby tonight.

I found a few options from the local Wayzyy guide:
• Option A — ...
• Option B — ...

If you want, I can also suggest something quieter or more lively.
```

---

## 11. Loading/Error States

### Loading
“Your concierge is preparing your trip plan…”

### Temporary failure
“I’m having trouble preparing that right now. Please try again in a moment.”

### Missing data
“I don’t have enough verified local information for that request yet.”

### Weather unavailable
“I can still help with your itinerary, but live weather information is temporarily unavailable.”

Never display raw stack traces or API errors to guests.

---

## 12. Accessibility

- Use readable font sizes.
- Maintain strong text/background contrast.
- Buttons should have clear labels.
- Forms should have visible labels.
- Keyboard navigation should work.
- Do not rely on color alone for status.
- Error messages should explain what needs correction.

---

## 13. Responsive Requirements

Desktop:
- Optimized for laptop presentation.

Mobile:
- Form remains readable.
- Buttons remain easy to tap.
- No horizontal scrolling.

---

## 14. Frontend Technology

Use the simplest reliable implementation.

Preferred MVP:
- HTML.
- CSS.
- JavaScript.

A React application is acceptable if the team is already comfortable with it, but it should not add unnecessary setup or dependency complexity.

---

## 15. Frontend Security

- No API keys in JavaScript.
- No Telegram bot token in browser code.
- No Claude key in browser code.
- No weather key in browser code.
- Send only required booking information to the webhook.
- Use HTTPS for deployed webhook/frontend communication.

---

## 16. Demo Optimization

The UI should make the story obvious:

**Click “Confirm Booking” → show automation status → open Telegram → itinerary arrives → send question → weather adaptation notification arrives.**

The booking simulator is a demonstration surface, not the product's primary value.
